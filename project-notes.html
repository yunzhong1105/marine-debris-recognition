NetScore 公式（輕量化獎）

Ω = 20·log₁₀(a² / (√p · √m))
  = 40·log₁₀(a) − 10·log₁₀(p) − 10·log₁₀(m)

a = 精確度   p = 模型大小(MB)   m = 運算複雜度(GFLOPs)
把公式展開才看得出重點

精確度的係數是 40，模型大小和 GFLOPs 各是 −10。也就是說精確度的影響力是模型大小的 4 倍。所以輕量化獎不該無腦選最小的模型，而該選「夠小之中最準的」。等有這個資料集上 n 和 s 的真實 mAP 之後，兩個都代入算一次 Ω 再決定，別憑 COCO 的數字猜。

2核心策略：長尾決定分數

這是整個專案最重要的一件事

mAP 是對 34 類取算術平均，每一類的權重都是 1/34 = 2.94%，與樣本數無關。全資料集只有 13 個框的 aluminum_packaging，和有 5,641 個框的 plastic_bottle，對分數的影響完全一樣。

換算成實際的投資報酬：

  • 把 plastic_bottle 從 0.85 提到 0.90 → +0.15 分
  • 把 aluminum_packaging 從 0 救到 0.50 → +1.5 分（10 倍）

試算晉級門檻：若 20 個頭部類別 AP 都做到 0.80，14 個尾部類別只有 0.30：

(20 × 0.8 + 14 × 0.3) / 34 = 0.594   ← 剛好卡在 0.6 門檻下面

尾部類別就是晉級與否的決定因素。換更大的模型、拉高解析度，主要幫助的是那些本來就做得不錯的頭部類別。真正的分數在 oversample、copy-paste augmentation、以及下面的細粒度混淆群。

細粒度混淆群（mAP 主要流失處）

這些類別在視覺上極難分辨，往往要判斷「裝什麼」而非「長什麼樣」：

  • plastic_bottle / non_food_plastic_bottle / non_pet_food_beverage_container
  • cup / takeaway_beverage_cup
  • foam_buoy_float / fishing_buoy_float / soft_float
  • fishing_net_rope / net_like_item / fishing_gear

另外 other(1,590) 和 anthropogenic_fragment(6,107) 是定義模糊的 catch-all，標註本身必有噪聲，而且會吃掉其他類別的 recall。

影像特性

  • 解析度混雜：主力 1108×1477 直式（約 8,400 張，像是標準化的調查拍攝），另有 4032×3024 手機原圖、820×547 小圖。

實際看圖的觀察

  1. 偽裝色（camouflage）：一張 95 框的圖裡，保麗龍碎片、漂流木、白色礫石在色彩與紋理上幾乎同構。這類圖靠低解析度抓不到。
  2. 難易度落差極大：也有很多是沙灘上一個寶特瓶佔滿畫面，基本白送。
  3. 漁業廢棄物場景：漁網、浮球、竹竿、漂流木交纏，框重疊嚴重。
標註品質很好

轉檔時 32,189 個框全數保留：零裁切、零退化框、零 iscrowd、零缺圖。省掉了通常要花的資料清理時間。

兩個關鍵設計決策

① labels/ 必須跟 images/ 同層

Ultralytics 找標註的方式是把影像路徑字串裡的 /images/ 直接換成 /labels/，副檔名換 .txt。這是硬編碼慣例，資料夾不能改名。

② 用檔案清單，不分資料夾

一般 YOLO 教學會叫你複製成 images/train/ 和 images/val/。這裡不這樣做——15k 張 JPEG 複製一份很浪費，要跑 5-fold 就得複製 5 次。改用 fold0_train.txt 每行一個絕對路徑，切分只是換一個文字檔。

資料根目錄解析（src/paths.py）

資料集不一定要放在專案裡。解析順序：

  1. $MDR_DATA 環境變數
  2. <專案>/data
  3. <專案>/../data（資料與專案並列時）

6資料前處理

coco_to_yolo.py

把 COCO 的 [x, y, w, h]（絕對像素、左上角）轉成 YOLO 的 cls cx cy w h（正規化、中心點）。

官方 category_id 本來就是連續的 0–33，直接對應 YOLO class id，不需要重新編號。

python src/coco_to_yolo.py
# → data/train_dataset/labels/ 底下 15,127 個 txt
# → configs/classes.yaml

make_split.py — 5-fold 分層切分

為什麼不能隨機切驗證集

aluminum_packaging 全資料集只有 13 個框。隨機切 90/10，val 平均只分到 1.3 個框，運氣差就是 0 個。

  • val 有 0 個框 → 這類完全沒有分數訊號
  • val 有 1 個框 → AP 只可能接近 0 或接近 1，擲硬幣

這一類佔 mAP 的 2.94%，於是總 mAP 會因為純粹的運氣上下跳 ±3 分。你做了一個真的有效、值 +1 分的改動，但雜訊有 ±3 分——你根本分不出來是改動有效還是運氣好，接下來所有決策都建立在噪聲上。

用的是 iterative stratification（Sechidis et al. 2011）。因為一張圖可能同時有好幾個類別，這屬於 multi-label 問題，一般的分層抽樣不適用。演算法會先安排最稀有的類別（它的自由度最低），每張圖分配給「目前最缺該類別」的那一折。

實際切分結果

folds: 5   images/fold: [3034, 3023, 3016, 3022, 3032]

class                          total    f0    f1    f2    f3    f4
aluminum_packaging                13     3     3     3     2     2
non_food_plastic_container        62    12    11    12    12    15
syringe_needle                   112    22    24    22    22    22
...

13 個框被切成 3/3/3/2/2，已是最佳分佈；其餘 33 類每折都 ≥11 個。這個演算法是決定性的，重跑結果完全一致。

但要誠實講

13 個框就算切得再完美也不可能穩定。真正的解法是 K-fold 交叉驗證——訓 5 個模型，每張圖都輪流當過一次 val，那 13 個框每一個都會被評估到。代價是訓練成本 5 倍。

實務折衷：日常快速迭代用單一 fold（看頭部類別夠了），要對尾部類別下最終判斷時才跑 K-fold。

8推論與評分

predict.py — 產生 submission.csv

python src/predict.py --weights runs/<name>/weights/best.pt \
                      --source data/splits/fold0_val.txt \
                      --out runs/<name>/submission_fold0val.csv
最關鍵的設定：conf=0.001、max_det=300

AP 是 precision-recall 曲線下的面積，算法是把所有預測框依信心分數由高到低排序，逐一納入，每步計算 precision 和 recall。

用 conf=0.25 過濾等於丟掉所有低分預測。那些預測大部分是錯的——但其中一小部分是對的，而且它們是唯一能把曲線推到高 recall 區段的東西。砍掉它們，PR 曲線就在中途被截斷，面積直接少一塊。

關鍵直覺：對 mAP 而言，多送一個低分的錯誤框代價幾乎是零；但漏掉一個物件，recall 永久少一塊。這是不對稱的，所以要盡量多送。

而 Ultralytics predict 的預設 conf 就是 0.25。用預設值產生 submission 會無謂損失大量分數——這是新手最常見的翻車點。

conf=0.25 是畫圖給人看用的，conf=0.001 是計分用的，兩者用途完全不同。

其他設計要點

  • Ultralytics 回傳中心點 xywh，官方要左上角，腳本用 xyxy 轉換
  • --source 吃資料夾或 .txt 清單，給 txt 時會先抽驗路徑是否存在
  • stream=True，15k 張的結果不會一次塞進記憶體
  • 跑完會算平均每張幾個框，低於 10 會警告（通常代表 conf 被誤設高了）

evaluation.py — 對齊官方計分

python src/evaluation.py --pred runs/<name>/submission_fold0val.csv \
                         --split data/splits/fold0_val.txt
刻意直接讀 submission.csv

而不是讀某個內部格式。這樣本地評分吃的就是你要上傳的那個檔案，座標慣例若有錯（中心點 vs 左上角、正規化 vs 絕對）本地就會現形，不會等到排行榜才發現。

  • 資料集的 image_id 是 hex 字串，pycocotools 內部會排序與雜湊處理，腳本全部重新映射成 int
  • --split 沒給會從 CSV 推斷範圍，但會警告：模型完全沒出框的圖會被排除，分數虛高
  • maxDets 設成 [1, 10, 300]——必須留三個值，否則 pycocotools 的 summarize() 會索引越界
  • 輸出每類的 gt 數、預測數、AP@0.5，由差到好排序，並算出離 0.6 門檻還差多少
尚未驗證的假設

官方的 x, y, w, h 假設是絕對像素、左上角（跟 train_label.json 一致），label_id 假設是 0–33。初賽開始後務必用官方 sample submission 對一次。要改也只是 predict.py 裡那幾行 writerow。

Ultralytics 訓練時印的 mAP50 是它自己算的，跟 COCO API 不完全一致——可以用來比較實驗好壞，不能用來判斷離 0.6 門檻多遠。

9遇到的問題與解法

環境Windows 沒有 Python
症狀
python.exe 只有 Microsoft Store 的 stub，執行無輸出。
原因
WSL 內是 Python 3.14，太新，PyTorch 沒有對應 wheel。訓練要跑 Windows 原生（WSL 只分到 7GB RAM）。
解法
winget install --id Python.Python.3.12 --scope user（user scope 免 UAC）
記憶體workers=8 → RuntimeError: bad allocation
症狀
堆疊指向 F.conv2d，看起來像 VRAM 不足。
真正原因
是主記憶體不足。mosaic 增強每個 sample 要組 2048×2048 緩衝，8 個 worker 各自預取，撐爆 16GB。實測 batch=4/workers=4 只用 6.09GB VRAM 完全正常。
解法
--workers 4
教訓
bad allocation 是 Windows 的 host 端 OOM，會被 CUDA 呼叫堆疊蓋掉，非常誤導。
記憶體驗證階段 CUDA OOM（短測試抓不到）
症狀
訓練正常，一進驗證就 CUDA error: out of memory。
原因
Ultralytics 上游 engine/trainer.py:293 把驗證 dataloader 設成 batch_size * 2。batch=4 訓練沒事，驗證變成 batch 8 @1024 就爆。
最陰險的地方
跟記憶體碎片累積有關：30 個 iteration 的 smoke test 會通過，1512 個 iteration 的半 epoch 才會炸。短測試抓不到，會在跑了一兩小時後才死。
解法
src/train.py 的 ValBatchCappedTrainer 子類覆寫 get_dataloader，在 mode == "val" 時把 batch 砍半以抵銷上游的 *2。用子類而非改 vendor，升級 ultralytics 時不會衝突。
順帶一提
Windows 不支援 expandable_segments，那條最常見的碎片化解法在這裡只會跳警告不生效。
記憶體訓練中途 CUDA OOM（闔上螢幕）
症狀
epoch 3 的 backward 崩潰，process 直接死掉（不是暫停）。
原因
訓練峰值 6.38G + 桌面 0.61G = 6.99G / 8.19G，餘裕僅約 1.2G。闔蓋觸發顯示模式切換，驅動重新配置 framebuffer，瞬間越線。
解法
降到 --batch 3（峰值 4.7G，餘裕 2.9G）。幾乎不花時間成本——epoch 時間由「處理多少張圖」決定，不是「跑幾個 iteration」。
附帶
powercfg /setacvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 0 等指令關掉闔蓋與睡眠。
路徑改名專案目錄 → 全面失效
症狀
import ultralytics → ModuleNotFoundError；configs 與 splits 內 15,127 條路徑全部指向不存在的位置。
原因
editable install 是用絕對路徑註冊的；生成的 split 清單也是絕對路徑。
解法
pip install -e vendor\ultralytics      # 重新註冊
python src/make_split.py --folds 5     # 重生成路徑
並把 make_split.py 改成從檔案位置自動推導根目錄（後來抽出成 src/paths.py），以後改名不會再壞。
續跑--resume 會挑錯 checkpoint
原因
原本傳 resume=True，Ultralytics 收到布林值會呼叫 get_latest_run()，挑「最近被寫入的」run 目錄——多個實驗並行時會接到別人的 checkpoint。
解法
改成直接傳 runs/<name>/weights/last.pt 的明確路徑，找不到就報錯而不是默默接錯。
好消息
Ultralytics 的 check_resume 把 batch、workers、imgsz 等列在允許覆寫清單裡（原始碼註解寫 "allow arg updates to reduce memory"），所以續跑時可以降 batch。
容器資料目錄沒有寫入權限
症狀
PermissionError: [Errno 13] ... '/home/jovyan/data/train_dataset/labels'
原因
掛進來的資料屬於 UID 1001，而你是 jovyan，落在 other，權限只有 r-x。目錄的寫入權限決定能不能在裡面新增檔案。
解法
sudo chown -R $(id -u):$(id -g) ~/data
容器部分影像不可讀，被靜默丟棄
症狀
605 images, 5 corrupt — 訊息寫 "corrupt"，實際是 Permission denied。
嚴重性
Ultralytics 直接跳過繼續訓練，不會停下來。0.8% 換算全資料集約 125 張圖連同標註被丟棄。
原因
非遞迴 chown 只改了目錄，個別影像檔案本身仍缺 other 的讀取權限。
解法
sudo chown -R $(id -u):$(id -g) ~/data
rm -f ~/data/train_dataset/labels.cache   # 這步不能省！
為什麼一定要刪 labels.cache

dataset.py:164 的快取雜湊是 get_hash(label_files + im_files)，只看檔名和大小。改權限不會改變任何一個，所以快取不會自動失效——那些圖會一直被排除，而且之後不再出現任何警告。

掃描時要看到 0 corrupt 才能往下跑。

容器libGL.so.1: cannot open shared object file
原因
opencv-python 完整版連結了 OpenGL 以支援 cv2.imshow() 那類 GUI 功能。動態連結在 import 時就發生，即使訓練從不開視窗也會炸。
解法
sudo apt-get install -y libgl1 libglib2.0-0
libglib2.0-0 是刻意一起裝的——裝完 libGL 之後下一個錯誤幾乎必定是 libgthread-2.0.so.0。
為什麼不用 headless 版
ultralytics 的 pyproject.toml 明確宣告 opencv-python>=4.6.0。換成 opencv-python-headless 後，只要再跑一次 pip install -e vendor/ultralytics，pip 就會把完整版裝回來，然後又壞掉。
容器/dev/shm 爆掉 → DataLoader worker bus error
症狀
unable to write to file </torch_...>: No space left on device (28)
DataLoader worker killed by signal: Bus error
原因
Docker 預設 /dev/shm 只有 64MB。PyTorch 的 DataLoader worker 透過共享記憶體把 tensor 傳回主行程，1280px × 8 workers 遠超過 64MB。
注意
跟前面的 bad allocation 不是同一件事——那次是主記憶體不足，這次是共享記憶體分區太小，主機記憶體再大也沒用。
解法 A
docker run --shm-size=8g 或 --ipc=host（最乾淨，但託管環境多半改不了）
解法 B
train.py 的 relax_shm_pressure() 偵測 /dev/shm 大小，小於 2 GiB 時自動切換成 file_system 共享策略——改用一般檔案傳遞 tensor，不需容器權限。
已知但未修train/val 共用同一個 labels.cache

Ultralytics 的快取路徑是 Path(label_files[0]).parent.with_suffix(".cache")，train 和 val 都指向同一個 labels/ 目錄，所以會寫到同一個檔案、互相覆蓋。

不是正確性問題——雜湊會驗證，不符就重新掃描。只是每次訓練啟動時 train 和 val 各要重掃一次（約 3 秒），從來不會命中快取。成本可忽略，暫不處理。

10必須理解的觀念

① mAP 是類別的算術平均，不是框的平均

這是整場比賽最重要的一句話。13 個框的類別和 5,641 個框的類別權重相同。所有優化決策都應該從這裡出發。

② AP 是 PR 曲線下的面積，而低分框是免費的

多送錯誤框的代價趨近於零，漏抓的代價是永久的。所以計分時 conf=0.001，不是 0.25。

③ 本地指標必須對齊官方指標

Ultralytics 的 mAP50 ≠ COCO API 的 mAP@0.5。前者可以比較實驗好壞，後者才能判斷離門檻多遠。

④ 驗證集的切法比模型架構更重要

切錯了，你的所有實驗結論都是噪聲。稀有類別必須刻意分層，最終判斷要用 K-fold。

⑤ YOLO26 的 end2end 與 mAP 的張力

one-to-many head（傳統）one-to-one head（預設）
訓練一個物件配對到很多個預測一個物件配對到剛好一個
推論產生重複框 → 需要 NMS天生不重複 → 不需 NMS
優點候選框密集，低分尾巴長快、部署簡單

one-to-one 是為降低延遲設計的。但對照觀念②，密集的低分候選框正是餵養高 AP 的東西。這場比賽主線只看 mAP、沒有延遲限制，所以大概率該用 end2end=False——但要實測，別預設接受 default。Ultralytics 官方 benchmark 把 mAP 和 mAP(e2e) 分成兩欄列，就是因為兩者確實有差。

⑥ Ultralytics 的路徑慣例是字串替換

影像路徑裡的 /images/ 換成 /labels/。這決定了目錄結構不能亂改。

⑦ editable install 記的是絕對路徑

搬動或改名專案目錄後必須 pip install -e 重新註冊，否則 import 直接失敗。

⑧ smoke test 至少要跑到第一次驗證結束

否則抓不到「驗證階段 batch×2 OOM」那類跟碎片累積有關的問題，會在跑了一兩小時後才死。

⑨ 三種記憶體要分清楚

種類典型錯誤訊息調整方式
VRAM（顯示記憶體）CUDA error: out of memory降 batch、降 imgsz
主記憶體 RAMbad allocation（Windows）降 workers
共享記憶體 /dev/shmBus error、No space left on device加大 shm 或改 file_system 策略

三者的錯誤訊息都會誤導人指向 GPU，實際原因往往不是。

11Git 與版控決策

追蹤的檔案（13 個）

.gitattributes  .gitignore  .gitmodules  README.md
configs/classes.yaml
requirements.txt  requirements.lock.txt
src/*.py
vendor/ultralytics   ← submodule 指標，不是 1030 個檔案

刻意不追蹤的東西

項目理由
*.pt權重會自動下載或由訓練產生。曾誤把 48MB 的 yolo26m/n.pt 放進 initial commit，後來改寫歷史移除，.git 從 44M 縮到 69K
configs/fold*.yaml生成物，且內含機器專屬絕對路徑——正是改名時壞掉的東西
data/、runs/、.venv/資料、輸出、環境

為什麼 vendor 用 submodule 而不是直接 commit

vendor/ultralytics 本身就是一個 git repo。直接 git add 會變成 "embedded repository"：外層只記路徑、內容沒進去，clone 下來是空目錄，而且 git 不會提醒。想真的塞進去得先刪它的 .git——那就把 1,030 個上游檔案變成自己的了，之後沒辦法 merge 新版。

submodule 只記一行：

160000 commit 98a9cfde3119079568620bd43c26bb541c61ac8d  vendor/ultralytics

這比 tag 更嚴格——tag 可以被上游移動，commit hash 不行。三週後要重現某次分數時，這個差別是實質的。

為什麼不能用 pip freeze > requirements.txt

  1. --extra-index-url 會消失。freeze 只輸出 torch==2.9.1+cu126，但 PyPI 沒有 +cu126 的 build，新機器直接報 No matching distribution。
  2. ultralytics 那行會毀掉 submodule 架構。freeze 產生 -e git+https://...ultralytics.git@<sha>#egg=ultralytics，會叫 pip 重新 clone 一份到 ./src/，繞過 vendor。結果是你對 vendor 的修改靜默失效。

所以分成兩個檔案：requirements.txt（3 個直接依賴，平常安裝用）和 requirements.lock.txt（36 個完整 pin，重現用，檔頭記錄了上述兩個陷阱）。
